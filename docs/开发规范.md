# SeerAPI 开发规范

本文约束 SeerAPI 的长期代码结构，尤其是发布构建和数据资源管线。

## 职责边界

- 数据下载协议、二进制解析、资源转换、事实归一化、SQLite 写入和发布 workflow 是不同职责。
  一个模块只拥有其中一类职责；调用方只能编排，不得重新实现下游规则。
- 发布时可确定的关联、图标转换和素材清单必须在构建期完成。运行时消费者只读取已发布的
  事实和 PNG，不重新猜测关系或转换 SWF。
- Unity 仓库已有的 PNG 只在发布清单中记录资源 key、内容摘要和不可变仓库 revision；
  不复制进消费者仓库或主数据 SQLite。不同业务图片必须复用同一清单协议，而不是直连
  可变 `main` URL。
- 网络协议必须集中在窄模块中，并具备明确失败语义。GitHub REST 限流等可预期故障只能使用
  已声明的替代协议，不能让调用方各自添加重试或静默降级。
- 新 schema、发布 metadata 或资源 manifest 改动必须同时提供 fixture、构建测试和下游消费
  约束；旧数据的兼容只允许停机/离线迁移，不进入正常运行路径。

## 代码大小与拆分

生产包和构建脚本的长期上限均为 800 行。限制的目的不是机械切文件，而是要求在模块接近
上限前识别真实边界：例如下载协议与资源目录快照、配置二进制解析与数据建模、SWF/PNG
转换与缓存、manifest 枚举与 SQLite 发布。

当前以下文件是过渡债务，必须逐步减少：

| 文件 | 当前职责债务 | 后续拆分方向 |
| --- | --- | --- |
| `scripts/build_seerapi_data_db.py` | 发布编排与多类资源/数据处理混合 | 按下载、解析、资源转换、manifest、写库拆分 |
| `scripts/build_new_content_index.py` | 内容索引读取、分类与输出混合 | 按输入 repository、分类规则、发布输出拆分 |

新功能不得继续堆入这些文件。每次迁出必须删除原实现，不保留同一规则的双实现或包装器，并
在提交中记录行数变化、受影响发布字段和验证命令。

## 验证与发布

- 构建脚本需要同时支持其 workflow 的直接执行方式和测试/工具导入方式。
- 每次职责迁移至少验证：相关 pytest、Ruff、`compileall`、`git diff --check`，以及一个不写
  发布文件的直接脚本 smoke。
- 正式 release 仍需运行完整构建及发布 gate；局部测试不能替代真实素材、schema 和 metadata
  的端到端验证。
